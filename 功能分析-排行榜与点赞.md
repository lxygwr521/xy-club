# 排行榜与点赞功能分析

## 一、排行榜（贡献榜）功能

### 1.1 功能概述

当用户新增题目时，系统自动累加该用户在 Redis 有序集合中的贡献分值。前端请求排行榜时，从 Redis ZSet 按分数倒序读取 Top 6 的贡献者，再通过 Feign RPC 调用 Auth 服务补齐用户昵称和头像后返回。

### 1.2 涉及文件

| 文件 | 层级 | 职责 |
|------|------|------|
| `xyclub-subject/.../application/controller/SubjectController.java` | Controller | 暴露 `POST /subject/getContributeList` 接口 |
| `xyclub-subject/.../domain/service/SubjectInfoDomainService.java` | Domain 接口 | 定义 `getContributeList()` 方法 |
| `xyclub-subject/.../domain/service/impl/SubjectInfoDomainServiceImpl.java` | Domain 实现 | 核心逻辑：写榜（add 时 +1 分）、读榜（Top 6 查询 + 用户信息补充） |
| `xyclub-subject/.../domain/redis/RedisUtil.java` | 基础设施 | ZSet 操作工具：`addScore`、`rankWithScore`、`zAdd` 等 |
| `xyclub-subject/.../infra/rpc/UserRpc.java` | 基础设施 | 封装对 Auth 服务的 Feign 调用，获取用户昵称和头像 |
| `xyclub-subject/.../infra/entity/UserInfo.java` | 基础设施 | 用户信息实体（userName, nickName, avatar） |

### 1.3 数据存储

#### Redis Key: `subject_rank`

| 属性 | 说明 |
|------|------|
| **数据类型** | ZSet（有序集合） |
| **Key** | `subject_rank` |
| **Member** | 用户登录 ID（`LoginUtil.getLoginId()`，通常是用户名） |
| **Score** | 贡献分值（Integer，即该用户新增的题目数量） |
| **容量控制** | 读取时只取 Top 6（索引 0~5），无上限写入 |
| **持久化** | 依赖 Redis 自身的 RDB/AOF 持久化策略 |

## 二、点赞功能

### 2.1 功能概述

点赞功能采用 **Redis 为主 + MySQL 持久化为辅** 的架构：
- **写操作**：点赞/取消点赞先写入 Redis（Hash 存储状态 + String 计数器），保证高并发下的响应速度
- **读操作**：从 Redis 读取用户的点赞状态和题目的点赞总数
- **持久化**：通过 XXL-JOB 定时任务，周期性将 Redis 中的点赞数据批量同步到 MySQL `subject_liked` 表
- **详情展示**：查询题目详情时，同时返回当前用户是否已点赞 + 该题目的点赞总数

### 2.4 工作流程

#### 2.4.1 点赞 / 取消点赞

```
POST /subjectLiked/add  (SubjectLikedController.add)
  │
  ├─ 校验: subjectId ≠ null, status ≠ null
  ├─ 注入: likeUserId = LoginUtil.getLoginId()
  ├─ DTO → BO 转换
  │
  └─ SubjectLikedDomainServiceImpl.add(subjectLikedBO)
       │
       ├─ hashKey = "1001:zhangsan"   // "{subjectId}:{likeUserId}"
       ├─ countKey = "subject.liked.count.1001"
       ├─ detailKey = "subject.liked.detail.1001.zhangsan"
       │
       ├─ 写入 Hash:  HSET subject.liked "1001:zhangsan" 1
       │
       ├─ 如果 status == LIKED (1):
       │    ├─ INCR subject.liked.count.1001        // 点赞数 +1
       │    └─ SET subject.liked.detail.1001.zhangsan "1"  // 标记已点赞
       │
       └─ 如果 status == UN_LIKED (0):
            ├─ 读取 count，如果 count > 0:
            │    └─ DECR subject.liked.count.1001   // 点赞数 -1
            └─ DEL subject.liked.detail.1001.zhangsan    // 移除点赞标记
```

**关键代码** (`SubjectLikedDomainServiceImpl.java:44-66`):
```java
@Override
public void add(SubjectLikedBO subjectLikedBO) {
    Long subjectId = subjectLikedBO.getSubjectId();
    String likeUserId = subjectLikedBO.getLikeUserId();
    Integer status = subjectLikedBO.getStatus();
    String hashKey = buildSubjectLikedKey(subjectId.toString(), likeUserId);

    redisUtil.putHash(SUBJECT_LIKED_KEY, hashKey, status);
    String detailKey = SUBJECT_LIKED_DETAIL_KEY + "." + subjectId + "." + likeUserId;
    String countKey = SUBJECT_LIKED_COUNT_KEY + "." + subjectId;
    if (SubjectLikedStatusEnum.LIKED.getCode() == status) {
        redisUtil.increment(countKey, 1);       // 点赞 +1
        redisUtil.set(detailKey, "1");          // 记录已点赞
        return;
    }
    Integer count = redisUtil.getInt(countKey);
    if (Objects.isNull(count) || count <= 0) {
        return;
    }
    redisUtil.increment(countKey, -1);          // 取消点赞 -1
    redisUtil.del(detailKey);                   // 移除点赞标记
}
```

#### 2.4.3 定时同步 Redis → MySQL（XXL-JOB）

```
XXL-JOB 调度中心 ──触发──→ SyncLikedJob.syncLikedJobHandler()
                              │
                              └─ SubjectLikedDomainServiceImpl.syncLiked()
                                   │
                                   ├─ 1. 从 Redis Hash "subject.liked" 读出全部 field-value
                                   │     同时删除已读出的 field（HSCAN + HDEL 逐条清理）
                                   │     redisUtil.getHashAndDelete("subject.liked")
                                   │
                                   ├─ 2. 解析每条数据
                                   │     key: "1001:zhangsan" → subjectId=1001, likedUser=zhangsan
                                   │     value: "1" → status=1
                                   │
                                   └─ 3. 批量写入 MySQL
                                        subjectLikedService.batchInsert(subjectLikedList)
                                        INSERT INTO subject_liked (...) VALUES (...), (...), ...
```

**关键代码** (`SubjectLikedDomainServiceImpl.java:118-139`):
```java
@Override
public void syncLiked() {
    Map<Object, Object> subjectLikedMap = redisUtil.getHashAndDelete(SUBJECT_LIKED_KEY);
    if (MapUtils.isEmpty(subjectLikedMap)) {
        return;
    }
    List<SubjectLiked> subjectLikedList = new LinkedList<>();
    subjectLikedMap.forEach((key, val) -> {
        SubjectLiked subjectLiked = new SubjectLiked();
        String[] keyArr = key.toString().split(":");
        subjectLiked.setSubjectId(Long.valueOf(keyArr[0]));     // 题目ID
        subjectLiked.setLikeUserId(keyArr[1]);                   // 点赞人
        subjectLiked.setStatus(Integer.valueOf(val.toString())); // 状态
        subjectLikedList.add(subjectLiked);
    });
    subjectLikedService.batchInsert(subjectLikedList);
}
```

**Redis getHashAndDelete 实现** (`RedisUtil.java:164-175`):
```java
public Map<Object, Object> getHashAndDelete(String key) {
    Map<Object, Object> map = new HashMap<>();
    Cursor<Map.Entry<Object, Object>> cursor =
        redisTemplate.opsForHash().scan(key, ScanOptions.NONE);
    while (cursor.hasNext()) {
        Map.Entry<Object, Object> entry = cursor.next();
        map.put(entry.getKey(), entry.getValue());
        redisTemplate.opsForHash().delete(key, entry.getKey());  // 逐条删除
    }
    return map;
}
```
这是典型的 **"读即清空"（Read-and-Clear）缓冲模式**，目的是防止数据重复同步。

核心原因

subject.liked Hash 的定位是临时写缓冲，不是永久存储。XXL-JOB 定时任务每次执行 syncLiked() 时，会把这个 Hash
里的所有字段全部读出并批量 INSERT 到 MySQL。如果不删，下一次定时任务触发时会把同样的数据再读出来再 INSERT 一遍，导致
MySQL 中出现重复记录。

使用 HSCAN 游标遍历 + HDEL 逐条删除，避免大 Hash 下的阻塞。

## 三、两个功能的关联点

排行榜和点赞是两个独立的功能模块，它们之间的关联比较松散：

| 关联点 | 说明 |
|--------|------|
| **共用 RedisUtil** | 两者都使用同一个 `RedisUtil` 工具类（位于 `xyclub-subject/domain/redis`），但操作不同的 Redis 数据类型和 Key |
| **共用 SubjectInfoDomainServiceImpl** | 排行榜的写入和读取、点赞状态的查询都收敛在同一个 Domain Service 中 |
| **共用 SubjectInfoBO/DTO** | 查询题目详情时，同时返回点赞信息（`liked`、`likedCount`）和贡献者信息（`createUser`、`createUserAvatar`）。排行榜列表也复用 `SubjectInfoBO`，通过 `subjectCount` 字段传递贡献分 |
| **共用 LoginUtil** | 排行榜写榜时获取当前用户、点赞时获取当前用户，都通过 `LoginUtil.getLoginId()` |
| **数据存储分离** | 排行榜只用 Redis ZSet（无 MySQL 持久化），点赞使用 Redis + MySQL 双写。两者在存储层完全独立 |

## 五、关键设计决策与注意事项

### 排行榜
1. **无 MySQL 持久化**：排行榜数据仅存于 Redis ZSet 中。如果 Redis 数据丢失，排行榜将归零，需要从 MySQL `subject_info` 表中重建。
2. **Top 6 硬编码**：`rankWithScore(RANK_KEY, 0, 5)` 固定取前 6 名。如需调整，需修改代码。
3. **跨服务 RPC 补充信息**：ZSet member 只存储用户名，用户昵称和头像通过 Feign 调用 Auth 服务实时获取。Auth 服务不可用时会返回空的 `UserInfo`。
4. **并发安全**：`ZINCRBY` 是原子操作，支持高并发写入，但多线程同时新增题目时不会出现计数丢失。

### 点赞
1. **读写分离**：写（点赞/取消）走 Redis，读（状态查询）也走 Redis。MySQL 仅作为异步持久化存储，不参与实时读写链路。
2. **同步策略**：XXL-JOB 定时从 Redis Hash 中 HSCAN + HDEL（读一条删一条），避免数据重复同步。同步间隔取决于 XXL-JOB 调度配置。
3. **幂等性**：`batchInsert` 会持续追加记录。用户反复点赞/取消会在 MySQL 中留下多条历史记录（通过 `status` 区分，且不走 update 合并）。
4. **点赞计数器持久化风险**：`subject.liked.count.{subjectId}` 是一个纯 Redis 计数器，如果 Redis 数据丢失，计数归零，与 MySQL 中实际点赞记录数可能不一致。
5. **详情查询时的 N+1**：当分页查询题目列表时，`getSubjectPage()` 方法目前未补充每个题目的点赞数和点赞状态，仅单条详情查询 (`querySubjectInfo`) 时才会补充。批量查询场景存在 N+1 风险。
6. **XXL-JOB 任务**：`syncLikedJobHandler` 是 XXL-JOB 的 Handler，需要在 XXL-JOB 调度中心配置对应的任务和 Cron 表达式后才会执行。
